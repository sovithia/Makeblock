Teach it — the concept

Open with the Grade 8 fair photos, then the year’s premise: same robot, professional tools. mBlock’s Python mode is a real editor — text, autocomplete, error messages. The first program is deliberately familiar: the square. They’ve built it in blocks (Grade 7) and read it in Python (Grade 8, Session 17); today they type it from a blank file. Familiar problem + new medium = confidence, not overwhelm.

Institute pair programming as this year’s standard: driver types, navigator reads ahead and catches errors; swap every 10 minutes. It’s how professionals work and it halves the syntax frustration of week one. Also set the error-message culture: an error message is information, not an insult — read it aloud, bottom line first.

Teach it — the concept

A function is a named behavior: define square(size) once, call it anywhere, change it in one place. Connect backwards: functions are to code what loops were to repeated blocks in Grade 7 — the next rung on the same ladder (don’t repeat yourself). The parameter is the power move: square(20), square(40) — one definition, infinite squares.

Build a small personal library today: square(size), polygon(n, size), celebrate() (LEDs + sound). This library literally gets imported into the capstone — tell them that now, so “write it well” has a reason. Naming matters: celebrate() reads like English; func2() reads like regret.
Python (mBlock → Python mode)
import mbot2, cyberpi def polygon(n, size): for i in range(n): mbot2.straight(size) mbot2.turn(360 / n) def celebrate(): cyberpi.led.on(255, 180, 0) cyberpi.audio.play('yay') polygon(5, 25) # pentagon, one line celebrate()
Watch out
  • The another-pair-can-use-it test is the real definition of a good function.
  • Watch for logic vs. syntax confusion: polygon(3, ...) turning 120° is correct — remind them of the exterior angle.

② Teach & Do — the core (45′)

10′Live-code square() together; call it three times with different sizes.
15′Pairs build polygon(n, size) — the 360/N rule becomes one line of math in code.
12′Design celebrate() freely: lights + sound + a wiggle; must be a single call.
8′Library review: swap code with another pair; can they use your functions without asking you?
＋ the 2-hour session — the other 65′ (② Teach & Do = the 45′ core above · ③ break 5′)
① Recap & Debug 10′

Run the swap test properly. Hand your library to another pair with no README and no talking, then watch what they get wrong. Every misuse is a naming problem or a parameter problem, and both are visible within seconds — which is why this is the real definition of a good function, not a nice-to-have.

④ Extend — to spec 25′
  • used cold, no questions Another pair calls your functions with no explanation given and none asked for.
  • polygon(n, size), 3 shapes One function, three different shapes, exterior angles correct in every case.
  • celebrate() as a single call Everything inside the function; nothing left over at the call site.
⑤ Engineering Log 10′

The library with a one-line comment per function saying what it does and what the parameters mean. This code is imported by the capstone in Session 15, so it is being written for a reader fifteen weeks from now — and that reader is usually its author.

⑥ Design Review 15′

The receiving pair reports what they got wrong. Criteria — was the confusion caused by a name or by a parameter? Both are free to fix today and expensive to fix during a build sprint.

Teach it — the concept

Sensors in Python return numbers you can hold in a variable: off = cyberpi.quad_rgb_sensor.get_offset_track(). That one line changes the relationship — in blocks, values flowed invisibly; in Python, students capture, print, compare and compute with them. Build the classic diagnostic tool first: a loop printing the live readings to the screen ten times a second (a dashboard, and their debugging best friend for the rest of the year).

This robot senses the floor and its own wheels — there is no ultrasonic anywhere on the Rover, so nothing here measures the air in front of it. Two numbers matter all year. The Quad RGB reports how far off-centre the line is (an offset, roughly −100…+100): push the robot along a line by hand and watch it swing negative–zero–positive — that number IS next week’s error signal. The encoders report how far each motor has turned in degrees: push the robot forward by hand and watch the angle climb — that number is Session 9’s ruler.
Python (mBlock → Python mode)
import cyberpi, mbot2, time mbot2.EM_reset_angle('EM1') while True: off = cyberpi.quad_rgb_sensor.get_offset_track() deg = mbot2.EM_get_angle('EM1') cyberpi.display.show_label( 'off=' + str(off), 16, 'top') cyberpi.display.show_label( 'deg=' + str(deg), 16, 'center') if cyberpi.quad_rgb_sensor.is_color('red', 'l1'): cyberpi.display.show_label( 'MARKER!', 24, 'bottom') time.sleep(0.1)

Teach it — the concept

Full control flow: if / elif / else and while. The vehicle is deliberately nostalgic — rewrite Grade 7’s wander mode in Python. But Grade 7’s robot escaped from a distance, and this one has no ultrasonic, so the same behaviour has to be built on a different sense: a taped boundary on the floor, and the Quad RGB probes that see it. Say that out loud as the day’s real lesson — the behaviour is not the sensor. Roam, notice the edge, back off, turn away, roam again: that shape is unchanged since Grade 7, and only one line of it knows what a sensor is.

Then introduce refactoring: improving code’s shape without changing its behaviour. Extract the escape manoeuvre into escape(), extract the sensing into on_edge(), name the magic numbers as constants (BACK_CM = 10), and re-run — identical robot behaviour, radically clearer code. Then land the point: because the sensing lives in on_edge(), swapping the robot’s eyes again would touch two lines. That “same behaviour, better shape” discipline is the heart of code quality, and it is a rubric line in the capstone code review.
Python (mBlock → Python mode)
import mbot2, cyberpi, random CRUISE = 40 # RPM: quick, but stoppable BACK_CM = 10 # far enough to clear tape def sees(probe): return cyberpi.quad_rgb_sensor.is_color( 'black', probe) def on_edge(): # no ultrasonic: the edge is a colour return sees('l1') or sees('r1') def escape(): mbot2.straight(-BACK_CM) mbot2.turn(random.randint(60, 120)) while True: if on_edge(): escape() else: mbot2.drive_speed(CRUISE, CRUISE)
Watch out
  • random.randint needs the import — a good ‘read the error’ moment.
  • ‘Why not what’ comments: # far enough to clear the tape, not # set BACK_CM to 10.
  • If the robot reverses onto the boundary and sticks there, BACK_CM is smaller than the wheelbase behind the probes. Measure it rather than guessing.
  • Tape the boundary wide — a thin line at speed is crossed between two sensor reads, and that is a genuine sampling lesson, not a bug.

② Teach & Do — the core (45′)

15′Rewrite wander in Python: while True + edge check + escape.
15′Refactor: extract on_edge() and escape(), name constants, add two comments that say WHY not what.
10′Arena test: does refactored wander behave identically? (It must — that’s the definition.)
5′On your lesson sheet: before/after code snippets — which would you rather debug at 11 pm?
＋ the 2-hour session — the other 65′ (② Teach & Do = the 45′ core above · ③ break 5′)
① Recap & Debug 10′

Record the behaviour before touching it — three arena runs with the original code, timed, boundary crossings counted. Without that baseline, "behaviour unchanged" is an opinion, and the whole point of the word refactoring is that the claim can be checked.

④ Extend — to spec 25′
  • identical, measured The same three-run measurement after refactoring, landing inside the spread of the before.
  • 0 magic numbers Every threshold a named constant, defined in exactly one place.
  • sensing in one function Exactly one function knows what the robot senses with. Change the colour of the tape and only that function needs reading.
⑤ Engineering Log 10′

⑥ Design Review 15′

Another pair reads the refactored version cold and states what the robot does. Criteria — could they say it without seeing the original, and did the named constants help, or did they just add a layer to chase?

Teach it — the concept

Resurrect Grade 7’s board question: why does the line follower zig-zag? Now they can answer it. Bang-bang control knows only three answers (hard left / straight / hard right) — it always overcorrects, overshoots, and corrects back: the wobble is built into the logic. The fix is one idea: make the correction proportional to the error. Slightly off → tiny steering nudge; far off → strong steering. In code it will be one line: steer = error × gain.

Teach it with the blindfold walk before any code: one student walks a taped line blindfolded; their partner may only say “left”/“right” (bang-bang) — watch them wobble. Then allow “a little left” / “way left” (proportional) — the walk visibly smooths. Ten minutes of theatre worth a thousand words. Then define terms on the board: error (the line offset they measured in Session 3), gain (how aggressively we respond), and predict together what too-low gain (drifts off curves) and too-high gain (wobbles again!) will look like tomorrow.
Watch out
  • Do NOT code today — the concept needs its own hour; tomorrow’s implementation then takes minutes.
  • The hand computation (offset × gain → two motor speeds) is the comprehension gate; don’t skip it.

② Teach & Do — the core (45′)

12′Blindfold line-walk, bang-bang vs. proportional instructions; debrief what changed.
12′Board the model: error → × gain → steering; connect error to Session 3’s offset number.
14′Paper-trace the algorithm on drawn scenarios: offset −60, gain 0.5 → motors? Teams compute by hand.
7′Predictions in the lesson sheet: sketch what gain-too-low and gain-too-high trajectories will look like.
＋ the 2-hour session — the other 65′ (② Teach & Do = the 45′ core above · ③ break 5′)
① Recap & Debug 10′

Walk it again, harder. The blindfolded partner now gets proportional instructions only — "a little left", "way left" — and the pair must agree in advance what "a little" means in steps. Quantifying the vague word is the gain, and discovering that is worth far more than being handed the term.

④ Extend — to spec 25′

  • 2 failure sketches Gain too low and gain too high, trajectories drawn before either is ever run.
  • the Grade 7 question, answered The wobble explained in one paragraph using error, gain and overcorrection.
⑤ Engineering Log 10′

The four computations with working, and the two predicted trajectories. Tomorrow the robot either matches these sketches or it does not — both outcomes are useful, and neither is available unless the sketches exist first.

⑥ Design Review 15′

Pairs present their answer to the board question that has been open since Grade 7. Criteria — does the explanation use error and correction, rather than "it's just jerky"? Two years of waiting has earned a real answer.

Teach it — the concept

Implementation day: read the offset, multiply by gain, split the result across the two tracks. The core is genuinely three lines — emphasize that a big idea can be small code. Then tuning: start with a low gain, raise it until the robot hugs curves, and keep going until it wobbles again (yesterday’s prediction comes true — applaud it, it means the model is right).

Tuning protocol is Session 15/13 discipline: one gain value → one timed lap → log it → change once. Teams produce a small gain table (gain / lap time / observation) and pick their champion value. Vocabulary upgrade: they are tuning a control loop — the same mathematics that keeps drones level and cruise control steady. They should know the thing they built today is not a toy idea.
Python (mBlock → Python mode)
import mbot2, cyberpi BASE = 45 # cruise RPM GAIN = 0.5 # tune me! while True: err = cyberpi.quad_rgb_sensor.get_offset_track() steer = err * GAIN # the whole idea mbot2.drive_speed(BASE + steer, BASE - steer)
Watch out
  • Function names below follow mBlock’s CyberPi Python API; minor names vary by version — the class rule is: trust the editor’s autocomplete.
  • If the robot flees the line instantly, the offset sign is inverted — flip the +/− and move on.
  • Same track and battery across tuning laps, or the table lies.

② Teach & Do — the core (45′)

12′Type the P-follower; first run at gain ≈ 0.3 — expect lazy curve-cutting.
22′Tuning sprints: gain table with 5+ values, timed laps, one change at a time.
8′Champion runs: best gain, three laps, best time recorded next to Grade 7’s bang-bang times.
3′On your lesson sheet: your gain table + the value where wobble returned.
＋ the 2-hour session — the other 65′ (② Teach & Do = the 45′ core above · ③ break 5′)
① Recap & Debug 10′

Run yesterday's predictions. Set the gain deliberately too low, then deliberately too high, and compare the real trajectories against the sketches drawn when no code existed. Predictions that held are satisfying; predictions that failed are where the mental model needs repair, and that is the more valuable of the two.

  • beat bang-bang both ways Smoother and faster than the Grade 7 times written on the earlier lesson sheets.
  • wobble-return gain found The value at which instability comes back, located and recorded rather than avoided.
⑤ Engineering Log 10′

The gain table — gain, lap time, observation — champion value circled, wobble-return value marked. Same track and same battery across the whole table, or it lies; note the battery level so a future reader can tell whether it did.

⑥ Design Review 15′

Pairs defend their champion gain. Criteria — is the choice supported by the table, and can they say what goes wrong on each side of it? A champion value with no neighbours tested is a lucky guess.

Teach it — the concept

Engineers don’t say “it looks smoother” — they show a graph. Today: log the error signal while driving (append offset values to a list, or print them and transcribe), then plot error-vs-time for bang-bang and for P-control. The bang-bang plot is a square wave bouncing between extremes; the P-control plot shrinks and settles. One picture, whole argument.

Pair it with lap-time data: P-control is usually both smoother AND faster — a rare free lunch, and worth noticing. Fast teams get the D-term teaser: error × gain still overshoots a little because it reacts to where the robot IS, not where it’s HEADING; adding a term based on how fast error is changing (the derivative) damps that. Even implementing nothing, knowing PID exists — and that they built the P — is the doorway out of this course into real control engineering.
Python (mBlock → Python mode)
errors = [] for i in range(200): # ~20 s of driving err = cyberpi.quad_rgb_sensor.get_offset_track() errors.append(err) steer = err * GAIN mbot2.drive_speed(BASE + steer, BASE - steer) time.sleep(0.1) print(errors) # copy out to plot
Watch out
  • Transcribing 200 numbers is misery — sample every 5th, or screenshot the console.
  • The conclusion sentence must cite the graph (‘peak error fell from ~90 to ~25’), not vibes.

Teach it — the concept

The Rover has no ultrasonic and no GPS. Everything it knows about where it is comes from counting how far its own motors have turned, and that is called dead reckoning — the same method that crossed oceans before satellites. The arithmetic is one line: a wheel of diameter D advances π·D for every full turn, so degrees convert to centimetres. But do not compute the constant from the sprocket — measure it. Command a long straight, lay a tape measure along what the robot actually did, and divide. Theory gives you a number; the floor gives you the right one, and on tracks those two are never the same because rubber slips.

Then the hard truth, and it is the one the capstone is built on: error accumulates and never cancels. Drive a 50 cm square four times round and measure the gap between where the robot started and where it finished — distance and heading, three runs, a spread rather than a number. Nothing is broken; skid steering scrubs the tracks sideways on every turn and a little of each turn is simply lost. That spread is the budget every later behaviour must live inside, and it is precisely why the mission ends by stopping on a colour marker rather than by counting centimetres. Dead reckoning gets you near. A sensor gets you there. Write that sentence on the board and leave it up until Session 20.

Teach it — the concept

The Rover already has its arms — they went on in Grade 8 and they have not come off. What changes today is that there are two of them and the language is Python. The arms are mirror images, on S1 and S2, so "open" is a large angle on one and a small angle on the other — the same physical word, two opposite numbers. That asymmetry is a fact about the metal, and the whole job of today’s code is to make sure no other line in the program ever has to know it. grip_open() knows. Nothing else does.

Then the session’s bigger idea: defensive programming — code that assumes mistakes will happen and contains them.
